## 三、算子开发规则（本项目）

1. **只能修改 kernel.asc**。main.asc/data_utils.h/CMakeLists.txt/run.sh/scripts 三件套是模板保护文件，提交时被忽略。
2. **单 launch 合同**：每轮评测恰好 launch 一个 kernel（MIX kernel 内可含多 Group，但只许一次 launch）。
3. **精度合同**：y int8 严格逐元素一致（0 容差）；yScale fp32 rtol=atol=1e-4。RINT 舍入为 round-half-to-even，先 round 后 clamp，顺序不可换。
4. **版本管理**（用户规则）：**错误版本不登记为新版本；只有提交 OJ 且分数提高才立版**。每版记录：父版本 SHA-256、唯一假设、候选 SHA-256、15 case 结果。
5. **单变量实验**：每次只改一个因素；父版本必须是稳定态（0/15 版本禁止派生）。
6. **非 kernel 文件完整性**：候选目录中 7 个非 kernel 文件必须与 V0 模板逐字节一致（sha256sum 校验）。
7. **禁用函数**：fprintf 等输出函数会在平台合规检查报错。

## 六、实验结果完整复盘

### 6.1 V11-FP32DIRECT 失败复盘（最重要的教训）

**假设**：三跳 cast 链 FP32(RINT)→int32→half(NONE)→int8(RINT) 在 RINT 边界引入额外舍入；直接 FP32→int8(RINT) 一跳可消除。

**为什么错**：
1. 三跳链的存在原因是 **dav-2201 硬件路径规避**：INT32→FP16 直接转换走 vconv_deq 路径导致 y 全零（优化日志 L118 实测记录），SetDeqScale(1.0f) 是中和该路径的必需防御，不是可选优化
2. **AscendC 标准量化路径就是 fp32→fp16→int8**（KG score 0.878/0.921 双重确认），fp32→int8 直转不在 api-precision.md 规范表内
3. 删除 Mins(127.0f) 打开了溢出路径：FP32 除法 ULP 可产生 127.00001，RINT 后 128 溢出 int8
4. blaze 官方参考实现在 Cast 前必须显式 Max/Min clamp——clamp 不是冗余是契约

**方法论教训**：修改前没有先问"这段代码为什么存在"。看似冗余的防御链往往有硬件层面的存在理由。**cannbot 审查 + KG 检索在提交前拦下了这次必然失败的提交**——三维核查（规范表/历史版本对照/参考实现）值得固化为提交流程。

### 6.2 本地多 shape 实验复盘（22 shape）

- (16,16,32) 模板形状 PASS——V6 kernel 数值链完全正确
- 其余 21 shape 全部 `File I/O failed at main.asc:79`——**失败在测试框架而非 kernel**：main.asc 的输入加载逻辑硬编码了 case0 的文件布局（input/case0/*.bin + 固定 shape），probe 脚本的数据布局与之不符

## 九、核心经验沉淀（可直接复用）

1. **OJ 提交正确格式**：`host_cpp: None`（JSON null）+ kernel.asc 走 files 参数。名称全小写查询。login 限流 60s。本记录 §2 有完整代码。
2. **本地无需 CANN 9.0.0**：cann-8.5.0 ccec 原生支持 dav-2201，配好 LD_LIBRARY_PATH（两层驱动路径+插件路径）+ CMAKE_PREFIX_PATH 即可完整编译运行验证。
3. **改防御代码前先查存在理由**：AscendC 里"看似冗余"的 cast 链/clamp 常是硬件路径规避（vconv_deq）或规范契约。三维核查：api-precision.md 规范表 → 历史版本同操作对比 → 官方参考实现。
4. **失败实验不立版本**（用户规则）：只有 OJ 分数提高才固化版本，否则工作区保留但不进版本链。
5. **本地测试框架要适配 main.asc 文件契约**：main.asc 硬编码 input/case0 布局，多 shape 测试需本地改造 main.asc（保护文件本地可改）或适配其布局。
6. **cannbot 技能栈位置**：`cannbot-skills/ops/ascendc-api-best-practices/references/`（api-precision.md 是 Cast 规范权威）、`cannbot-skills/ops/ascendc-code-review/core/methodology.md`（审查方法论）；blaze 参考：`ops/ascendc-blaze-best-practice/assets/blaze_custom/epilogue/block_epilogue_pertoken_quant_single_pass.h`。
7. **kg-tools 查询**：POST https://ascend.wiki/search，header `X-API-Key`（测试 key 可用），body `{"query":"...","with_neighbors":true}`；中文/精确 API 名查询得分更高；cypher 慢、/source 常NODE_NOT_FOUND——优先 /search。
