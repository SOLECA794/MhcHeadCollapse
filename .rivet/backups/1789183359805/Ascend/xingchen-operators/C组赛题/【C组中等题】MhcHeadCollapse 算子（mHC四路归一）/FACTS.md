### F2.1 计时单位是微秒（μs），不是毫秒

**证据**: `MhcHeadCollapse_优化全记录_2026-09-08.md:49`（明确论证）、`迭代优化记录.md:1211`（勘误小节）

**✅ 实验 C 已执行（2026-09-11），双重独立证据确证 μs；并已定位 ms 混乱的确切来源**：

0. **★ 混乱来源已定位（2026-09-11 新证据）**：CLI 的 `ms` 后缀是**硬编码**的，不是平台返回的。
   `cannjudge-submit-plaintext/cannjudge_cli.py:224-225`：
   ```python
   time_ms = tc.get("time", "N/A")
   print(f"  Case {idx + 1}: {tc_status} | precision: {precision} | time: {time_ms}ms")
   ```
   而 API 原始返回里 `time` 是**裸数字**（如 `"time": 2.12`），**无单位字段**。
   → 任何人看到 CLI 输出都会以为单位是 ms。**这就是"时间单位争议"的根因。**

1. **物理反推（决定性）**：Case1 数据量 312B，若单位是 ms → 143.7 KB/s；
   Case5 数据量 50KB，若单位是 ms → 11.5 MB/s。均比任何 NPU 慢数个数量级。
2. **启动开销量级**：若单位是 ms，则 Case1（仅 16 个元素）耗时 2.94——同样荒谬。

⚠ **但 `迭代优化记录.md:75-79` 的用例表至今仍写 `ms`**，与 :1211 的勘误直接矛盾。
读到 :75-79 的人会得到数量级错误的结论。**以本文件为准：单位是 μs。**

**F1.1** 算子做四步融合：RMS 归一 → 门控线性投影 → sigmoid → 加权折叠。输出维度由 `nH` 变为 `H`。
证据: `赛题.md:1-40`（算子说明与数学定义）

**F1.2** 算子声明为纯 SIMD（AIV_ONLY），**无任何 matmul 调用**。
证据: `versions/v116_vsync_batched/code/op_kernel/mhc_head_collapse.cpp:609`(`KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY)`)

**F1.3** 评测为 per-call 端到端计时，5 个固定 case，`ranking_submission_mode=latest`（后提交覆盖前次）。

**关键结论**：
1. **标量指令（scalar）是最大单项**，占 39~46%，**是向量计算（8~16%）的 2.5~5 倍**。

### F2.1f ★★ 真实带宽标定 —— 实测 109 GB/s（F2.6 的 200 是估算，高估 83%）

用 Case5 的 mte2 实测反推：

| 项 | 值 |
|---|---|
| 单 block 搬运 | x(16KB) + w(32KB) + base/scale(36B) = 48KB |
| 8 block 总搬运 | x(128KB) + w(256KB) = **384KB** |
| mte2 实测 | **3.611 μs** |
| **有效带宽** | **384KB / 3.611μs = 109 GB/s** |

⚠ **F2.6 用的 200GB/s 是估算值，实测只有 109 GB/s（高估 83%）。**

**对 F2.6 结论的影响**：F2.6 曾用 "240KB @200GB/s = 1.23μs ≈ 实测 floor 差 1.18μs"
论证"floor 里含可消除的重复 DMA"。按实测 109GB/s 重算，240KB 需 **2.25μs**，
与 1.18μs 的 floor 差不吻合。

→ **F2.6 的归因需要重新审视**：floor 差（1.18μs）小于纯 weight 搬运差（2.25μs），
说明 floor 组成比原先设想的更复杂。此项标记为 **待重新验证**（见 §A）。

另注：Case1 的 mte2 = 1.721μs 但数据量仅 288B → 说明该 1.72μs 是**固定启动开销**，
不是带宽受限。

| case | Task Dur | aiv_time | scalar | mte2 | vec | mte3 |
|---|---|---|---|---|---|---|
| Case1 (BD=1) | 7.82 | 7.173 | **3.319 (46%)** | 1.721 (24%) | 0.554 (8%) | 0.003 |
| Case5 (BD=8) | 15.14 | 13.974 | **5.473 (39%)** | 3.611 (26%) | 2.231 (16%) | 0.153 |

**三条关键洞察**：

1. **Case1 的 mte2 = 1.721μs，但数据量仅 288B**
   → 288B/1.721μs = **0.17 GB/s**，荒谬。
   → **这 1.72μs 是 DMA 启动延迟，不是带宽传输**。DMA 有其自身的固定代价。

2. **Case1 的 aiv_time（7.173μs）是 Case5（13.974μs）的一半，但数据量只有 Case5 的 1/170**
   → **Case1 完全由固定开销主导，与数据量无关**。
   → 这解释了为什么 Case1 的全榜最优（2.12）与最差（5.94）差 2.8 倍，
     而 Case5 的最优（4.52）与最差（7.74）只差 1.7 倍。

3. **两个 case 的 scalar 占比都最高（46% / 39%），与 shape 无关**
   → 这是**真正的共性瓶颈**。历史文档聚焦 DMA 与归约原语，方向有偏。

**修正后的 floor 模型**：
```
floor ≈ 固定部分(启动 + 标量控制流) + 数据相关部分(mte2 + vec)
```
- 固定部分：**1.7μs 的 DMA 启动 + 3.3μs 的标量开销** ≈ 5μs（Case1 实测 7.17）
- 数据相关部分：Case5 比 Case1 多出的 6.8μs aiv_time

**优化含义**：
- 削 **scalar**（最大项，且与 shape 无关）→ 对所有 case 都有效，尤其是 Case1
- 削 **mte2 启动延迟**（1.7μs 固定）→ 对 Case1 收益最大
- **换归约原语**：只影响 vec（占比 8~16%，第三位）→ **ROI 最低**

### F2.1m ★★ 本地测量精确性审计（回答"能否绝对精确"）

**结论：不能做到绝对精确，但可以做到"相对可靠"。** 三层原因：

**① 计时口径不同（最主要）**
本地是 `aclrtSynchronizeStream` + 主机墙钟；OJ 口径未知（F2.1k）。
这不是精度问题，是**量纲不同**——两者测的不是同一个东西。

**② 主机侧噪声大，且 CPU 只有 1 核**
实测 4 次 `mhc_percall 4 4 1`：

| 次 | per_call | streamed | launch |
|---|---|---|---|
| 1 | 17.313 | **4.419** | 12.894 |
| 2 | 18.905 | **4.346** | 14.560 |
| 3 | 16.717 | **4.468** | 12.248 |
| 4 | 17.794 | **4.454** | 13.340 |

- `per_call`：极差 **2.19μs（±6.5%）** ← 抖动大
- `streamed`：极差 **0.12μs（±1.4%）** ← 稳定

⚠ **`nproc = 1`（单核）**——launch+sync 开销（12.2~16.3μs）是 kernel 本体的 3~4 倍，
且这个开销**主要由主机侧单核驱动**。这是本地噪声大的根因。

**③ `streamed` 不等于纯 kernel 时间**
实测 shape 依赖性：

| shape | 数据量 | streamed |
|---|---|---|
| n=4 h=4 outer=1 | 288 B | 4.35~4.47 |
| n=8 h=128 outer=8 | 384 KB | 4.30~4.45 |
| n=8 h=512 outer=32 | 5.2 MB | **11.087** |

小 shape 下 streamed 恒定 ~4.4μs（不随数据变），大 shape 才增长
→ **该指标含一个 ~4.4μs 的固定主机底噪**，纯 kernel 时间需扣掉它。

**可行的提精度手段**（按 ROI）：
1. **用 `streamed` 而非 `per_call` 做版本对比**（噪声 1.4% vs 6.5%）
2. **取多次最小值**（min 比 mean 更接近真值，剔除调度抖动）
3. **固定 NPU 频率**（当前空闲 800MHz / 满速 1650MHz，未锁定）
4. **加 `taskset` 绑核**（单核环境下减少迁移）
5. ❌ 不可能消除：本地与 OJ 的口径差异

**正确用法**：本地数字用于 **A/B 版本相对比较**（同口径下差值可信），
**不可**用于预测 OJ 绝对分数。

### F2.1n ★★★ 标量热点定位 —— scalar 46% 花在哪（v111/v116 静态定位）

F2.1e/F2.1j 确认 scalar 是最大单项（39~46%）。本项**定位到具体代码**。

> **正确结论见**：F2.1j（floor 归因重做）、F2.1n（标量热点定位）。

探针实测 floor（`迭代优化记录.md` 探针数据节）：Case3/4 = 2.2μs，Case5 = 3.38μs。
榜首 Case3/4 实测 2.84/2.92μs —— **低于 Case5 的 floor**，这在"floor 是常量"的模型下自相矛盾。

**解释**：P1 探针只清空 `ProcessVectorRow`，而 weight DMA 在 `Process()` 内仍执行（F2.5）。
按 F2.5 的搬运量差 (256−16)KB = 240KB，若有效带宽 ≈200GB/s：
`240KB ÷ 200GB/s ≈ 1.23μs`，与实测 floor 差 `3.38 − 2.2 = 1.18μs` **高度吻合**。

**含义**：所谓"per-call floor"里有约 1μs 是**可消除的重复 DMA**，不是不可压缩的启动开销。
这直接影响"kernel 藏进 floor"这条归因是否成立。
