【定位时间单位混乱的确切根因】
CLI 的 ms 后缀是硬编码的，不是平台返回：
  cannjudge_cli.py:224-225
    time_ms = tc.get("time", "N/A")
    print(f"  Case {idx+1}: {tc_status} | precision: {precision} | time: {time_ms}ms")
API 原始返回是裸数字（"time": 2.12），无单位字段。
→ 这就是 ms/μs 争议的根源，此前无人定位。

【重大发现：平台公开 best_time（每 case 理论下限）】
API 每个测试点带 best_time 字段，全榜完全一致：
  Case1-5 best_time = 2.12 / 2.12 / 2.48 / 2.48 / 4.36（合计 13.56）
  本队 kkio-       = 5.72 / 4.56 / 4.28 / 4.32 / 7.74（合计 26.62，1.96x）

关键结构洞察：
  Case1(outer=1) 与 Case2(outer=4)，best 都是 2.12
  Case3(outer=1) 与 Case4(outer=2)，best 都是 2.48
→ Case1-4 由固定 floor 主导，与数据量无关
